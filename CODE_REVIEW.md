## 3. Overall quality assessment

**Grade: B for the CLI, C− for the apps.** For an AI-scaffolded personal tool this is in good shape: the architecture is genuinely sound — a shared `BookkeeperCore` framework with `actor`-isolated services, platform front ends kept thin, credit-card debit/credit semantics centralized in `TransactionType`, and session-level caching in `HistoryMatcher` that shows real performance thought. The custom terminal UI (raw mode, ANSI drawing, searchable hierarchical pickers) is well beyond boilerplate.

The weaknesses are typical of primitive-AI-era generation:

- **Facade completeness**: the iOS and Watch targets *look* finished but key wiring is stubbed (credential persistence, AI service injection, dashboard stats hardcoded to "0", Watch `refresh()` does nothing). The code compiles, which hides how much is missing.
- **Silent-failure bias**: errors are frequently swallowed into defaults — unparseable Claude responses become "Uncategorized, confidence 0"; a category that doesn't match any Zoho account becomes `accountId: ""` sent to the API; `try?`/`try!` in view code.
- **Duplication**: `categorizeTransaction` exists twice (CLI + `TransactionEditorViewModel`) with identical bugs; account/category/vendor fetch logic repeated in three places.
- **Test theater**: 4 tests that assert enum display names, not runnable via any scheme. Effectively zero coverage of the actual logic (JSON parsing, history matching, cache).

## 4. Bugs found

Severity: 🔴 crash/data-risk · 🟠 broken feature · 🟡 correctness/robustness · ⚪ minor.

### 🔴 B1 — String-index crash in Claude response parsing
`Projects/BookkeeperCore/Sources/Services/ClaudeService.swift:142-144`
```swift
jsonString = String(response[jsonStart.lowerBound...jsonEnd.upperBound])
```
`upperBound` of `range(of: "}")` is the index *after* the brace. A closed range through it (a) includes one extra character, and (b) **traps at runtime when the response ends exactly with `}`** — i.e. whenever Claude returns bare JSON without a markdown fence, which is common. When it doesn't crash, a trailing `` ` `` from a code fence makes `JSONDecoder` fail and the suggestion silently degrades to "Uncategorized". Fix: `jsonStart.lowerBound..<jsonEnd.upperBound`.

### 🟠 B2 — iOS AI suggestion feature is dead
`Projects/App/Sources/Views/TransactionEditorView.swift:9-24, 158-163`
The view model accepts `claudeService`, `zohoClient`, `bankAccountId` in its initializer, but the view constructs it with none of them; the `onAppear` block that was supposed to inject the service is an empty stub (source of the compiler warning). "Get AI Suggestion" is enabled when `appState.claudeService` exists, then always fails with "AI service not configured". History refinement is likewise unreachable in the app.

### 🟠 B3 — iOS app forgets credentials on every launch
`Projects/App/Sources/App/AppState.swift:116-123`
`loadSavedConfiguration()` and `saveConfiguration()` are TODO stubs. Users must re-enter six credential fields per launch, which makes the app unusable in practice. This is the single biggest blocker for the phone-first direction.

### 🟠 B4 — Empty `accountId` sent to Zoho when lookups miss
`Projects/CLI/Sources/ZohoBookkeeperCLI.swift:304-319, 336-347, 351-362` and duplicated in `TransactionEditorViewModel.categorizeTransaction`
`searchAccountByName(...)?.accountId ?? ""` — if the chosen category (or the hardcoded "Owner's Equity"/"Sales" accounts) doesn't match a Zoho account, the request is sent with an empty account ID instead of failing fast. Zoho either rejects it (opaque error) or worse. Commit 03add42 already fought a variant of this class of bug. Should `throw` when the lookup returns nil.

### 🟠 B5 — Saving a Refund/Skip type silently marks it processed
CLI `categorizeTransaction` case `.refund, .skip` does nothing remotely, but the caller (`ZohoBookkeeperCLI.swift:219-227`, and `TransactionEditorViewModel` which calls `markProcessed` unconditionally) records the transaction as processed in the local cache. Select "Refund" → SAVE and the transaction vanishes from future runs while remaining uncategorized in Zoho. Refund should either be implemented or removed from the type-cycle; Skip-via-save should behave like the SKIP button (markSkipped) at most.

### 🟡 B6 — Invalid Anthropic model ID
`Projects/BookkeeperCore/Sources/Extensions/AnthropicModel.swift:44`
`claude46Opus = "claude-opus-4-6-20260219"` — Opus 4.6 has no date-suffixed ID; the real string is `claude-opus-4-6`. Currently unused at runtime (default is `.latestSonnet` → `claude-sonnet-4-5-20250929`, which is valid but no longer the newest model), but `latestOpus` would 404. While touching this file, consider adding current models (`claude-sonnet-4-6`, `claude-sonnet-5`, `claude-opus-5`) and repointing the `latest*` shortcuts.

### 🟡 B7 — Cache save is fire-and-forget on the error path
`Projects/CLI/Sources/ZohoBookkeeperCLI.swift:154-159`
```swift
defer {
    terminal.disableRawMode()
    Task { try? await cacheService.save() }
}
```
If `run()` exits via a thrown error, the detached Task races process exit and the session's processed/skipped marks can be lost. Normal paths save explicitly, so impact is limited to error exits — but it's exactly then that you'd want state preserved. `defer` can't await; restructure with `do/catch` + explicit `await save()`.

### 🟡 B8 — Dashboard statistics are hardcoded zeros; `try!` in view init
`Projects/App/Sources/Views/DashboardView.swift:12-14, 232-234`
`StatBox(title: "Processed", value: "0", ...)` etc. never call the existing `getCacheStats()`; and the view model is built with `try! CacheService()`, which crashes the app if the cache directory can't be created (the CLI and `AppState` both handle this failure gracefully).

### 🟡 B9 — Nondeterministic history-match tie-breaking
`Projects/BookkeeperCore/Sources/Services/HistoryMatcher.swift:115-121`
`counts.sorted { $0.value > $1.value }` on a dictionary: ties are ordered arbitrarily, so a vendor with e.g. 2×"Software" / 2×"Subscriptions" can flip categories between runs. Add a secondary sort key (name) for stability. Also, the majority check `count > expenses.count / 2` counts expenses with a nil category in the denominator.

### ⚪ Minor
- **M1** — Cache directory typo: `~/.zoho-ai-bookeeper` (`CacheService.swift:14`). Cosmetic, but a rename must migrate existing caches.
- **M2** — TUI: when the type isn't Expense, the Vendor row renders "N/A" but is still focusable and Enter opens the vendor picker (`TransactionEditor.swift` navigation doesn't skip `.vendor`).
- **M3** — `SearchablePicker` lets Enter select a parent/header row in the hierarchical category picker; if parents aren't real Zoho accounts this funnels into B4.
- **M4** — `TerminalSpinner` draws from a background DispatchSource while the main thread may also write to stdout — interleaved escape sequences can garble a frame.
- **M5** — `Logger` prints to stdout; any `logger.*` call while raw mode is active corrupts the TUI (e.g. `ClaudeService` error logging mid-spinner).
- **M6** — `TransferDetector` and `DashboardViewModel.getCacheStats()` are dead code (never called).
- **M7** — `config.json` (real secrets) is bundled as a framework *resource*, so credentials are copied into every built app bundle. Acceptable for a personal CLI; unacceptable for any distributed iOS build — replace with Keychain before TestFlight.
- **M8** — `ClaudeService.service` is `nonisolated(unsafe)` inside an actor — works, but reads as a concurrency-checking suppression; SwiftAnthropic's service is used from the actor only, so this can likely be plain `let` isolated state.
- **M9** — Watch app is a shell: `WatchState.refresh()` sets `lastUpdated` and nothing else; the complication always renders 0. Needs App Group/Watch Connectivity plumbing to be real.

## 5. Recommendations (ordered)

1. **Fix B1** (one-character fix, prevents crashes and silent "Uncategorized" degradation) and **B4/B5** (correctness of what gets written to your books). These affect the CLI you actually use.
2. For the iOS push: **B3 (Keychain persistence) → B2 (inject services into the editor VM) → B8**, then extract the duplicated `categorizeTransaction` into BookkeeperCore so CLI and app can't drift.
3. Add a testable scheme and put tests around `parseClaudeResponse` and `HistoryMatcher` — they're pure logic and carry most of the correctness risk.
4. Refresh `AnthropicModel` (B6) — the default model is a year old; newer/cheaper models exist.

## 6. Resolution log

All issues were resolved on 2026-08-16, immediately after the review. What actually changed, per issue:

### The app rewrite (resolves B2, B3, B8) — commit `e64d005`

Rather than patch the scaffold, `Projects/App` was rewritten (design rationale in `Projects/App/DESIGN.md`):

- **B3 (credentials never persisted)** → new `KeychainCredentialsStore` in BookkeeperCore stores the whole `FullConfiguration` as one Keychain item, behind a `CredentialsStore` protocol (`InMemoryCredentialsStore` for tests/previews). `AppModel.bootstrap()` restores it at launch; `submitCredentials` verifies against Zoho *before* saving. Setup also accepts a pasted CLI `config.json` (imports the category hierarchy too).
- **B2 (AI suggestion unreachable)** → the old `TransactionEditorView`/`TransactionEditorViewModel` pair is gone. `ReviewSession` owns the per-account triage queue and calls the new `SuggestionPipeline` (Claude + history refinement in one call), with one-ahead prefetch and graceful degradation to a manual draft when the API is unreachable.
- **B8 (hardcoded dashboard stats, `try!`)** → the home sidebar's stat tiles read live `CacheService.getStats()` via `Workspace.refreshCacheStats()`; no force-tries remain in view code.
- The BookkeeperCore `ViewModels/` (all three) were deleted with the old views.
